# SpeedRave — Full Code Review (October 2026)

**Scope:** The whole repository at `main` @ `2f9edec` ("Change Seed Flash Text", mod version 1.2.0): every file under `Source/`, plus `README.md`, `.gitignore` and `.gitattributes`.
**Type:** Inspection only. No source files were changed. This document is the only change.
**Areas covered:** security, bugs and correctness, code quality, performance, accessibility and UX.

## How this review was done and its limits

- Every line of the ~2,800 lines of C# and project files was read by hand. Git history was used to date regressions (mainly `f4fdeb5`, the large "Code Review Done by Gemini" commit, and `2cb2b6d`, "Fix Autosplitter for All Endings").
- **The project could not be compiled or run.** It references `Assembly-CSharp.dll`, Unity and BepInEx DLLs from a hard-coded Steam path (see Q-1), and those DLLs are not in the repository. The game's own classes (`DoorBehavior`, `FoodControl`, `TitleScreenControler`, `PersistControl` and others) were therefore **not decompiled or inspected**.
- Each finding has a confidence label:
  - **Confirmed**: follows directly from this repository's code.
  - **Likely**: follows from this code plus a reasonable assumption about game, Unity, BepInEx or LiveSplit behaviour. The assumption is stated.
  - **Verify**: depends on game behaviour that someone should check in-game before acting.
- Severity is judged for a speedrun mod. Anything that silently corrupts timing, breaks set-seed reproducibility or destroys user data is rated high, because it affects leaderboard runs.

## 1. Bugs and correctness

### B-1 — High — Instant Restart does not re-seed set-seed runs *(Confirmed)*

`GUI.cs:707-716`:

```csharp
if (Plugin.SeedEnabled.Value)
{
    if (Patches.SetSeedPatchs.randomSeed)
    {
        Patches.SetSeedPatchs.Init();
    }
    ...
```

`SetSeedPatchs.Init()` is the only code that resets the seeded RNG stream (`SetSeedPatchs.state`, `Patches/SetSeed.cs:75-101`). Init normally runs as a prefix on `TitleScreenControler.StartGame`. Instant Restart skips `StartGame` and loads `Sewer_Start` directly (`GUI.cs:731`). It only calls `Init()` when **random** seed mode is on.

With a **set** seed, `state` therefore carries on from wherever the previous attempt left it. The restarted run shows "Seed: N / Set Seed" in the flash text but generates a different layout from a title-screen start with seed N. This silently undermines the headline set-seed feature.

The GUI buttons make it worse. "Set Seed" and "Paste Seed" (`GUI.cs:484`, `GUI.cs:510`) call `UnityEngine.Random.InitState(seed)`. That seeds Unity's *global* RNG (the "messy" state), not `SetSeedPatchs.state`, so it has no effect on the seeded stream. "Last Random" (`GUI.cs:488-495`) does not seed anything. The three buttons behave inconsistently, and none of them does what a user expects.

**Fix:** Always call `Init()` from Instant Restart when seeding is enabled. Make `Init()` the single place that seeds `state`, and have the GUI buttons only set `Seed` and `randomSeed`. Optionally add a `SetSeedPatchs.Reseed()` helper with a clear name.

### B-2 — High — Instant Restart wipes **all** PlayerPrefs mid-run *(Confirmed)*

`GUI.cs:693-705`:

```csharp
if (Plugin.ClearSaveOnStart.Value)
{
    var titleController = UnityEngine.Object.FindObjectOfType<TitleScreenControler>();
    if (titleController != null) titleController.ClearSaveData();
    else { PlayerPrefs.DeleteAll(); PlayerPrefs.Save(); }
}
```

Mid-run there is no `TitleScreenControler` in the scene, so the `else` branch always runs. `PlayerPrefs.DeleteAll()` removes every key the game stores, not just the save. That likely includes audio volume, mouse sensitivity, resolution and quality preferences, and anything else the game or other mods keep in PlayerPrefs.

Three things make this High rather than Medium:
- `ClearSaveOnStart` defaults to **true** (`Plugin.cs:85`, see B-14).
- The restart hotkey is handled **outside** the `TrainerEnabled` check (`GUI.cs:157-160`), so F6 is always live.
- F6 is a common key for other tools: OBS hotkeys, overlays, browser refresh habits.

**Fix:** Mirror what `ClearSaveData()` deletes. Ideally call it via reflection on a cached instance, or decompile it and delete the same keys with `PlayerPrefs.DeleteKey(...)`. Never use `DeleteAll`. Consider requiring a modifier (Ctrl+F6) or only allowing restart while a run is active.

### B-3 — High — After the first ending, LiveSplit game time and the on-screen timer stay frozen *(Confirmed in code; regression since `2cb2b6d`)*

Commit `2cb2b6d` ("Fix Autosplitter for All Endings") deliberately supported several endings in one run (`plagueEnding`, `spaceEnding`, `trueEnding`, `endingCount`). The current code breaks that:

1. Entering an `EndingTeleporter` calls `NotifyLoadingStarted()`. That sets `isLoading = true` and pauses LiveSplit game time (`timerPaused = true`) (`Patches/AutoSplitter.cs:38-47`, `AutoSplitter.cs:22-32`).
2. When the ending scene loads, `Autosplitter.OnSceneLoaded` takes the `HandleEnding` branch (`AutoSplitter.cs:98-101`). That branch does **not** set `justLoadedScene`. `HandleEnding` then calls `OnScreenTimer.StopTimer()`, which sets `IsRunActive = false` and `IsEnded = true`, and queues `pausegametime` (`AutoSplitter.cs:367-374`).
3. The only code that clears `isLoading` is `OnScreenTimer.Update` (`OnScreenTimer.cs:74`), and it requires `IsRunActive && !IsEnded`. After step 2 that can never be true again until `StartTimer()`.
4. As a result, `isLoading` stays `true` for the rest of the run:
   - `NotifyLoadingStarted` early-returns on every later door.
   - `UpdateAutosplitter` never sends `unpausegametime`, because its condition `timerPaused && !isLoading` (`AutoSplitter.cs:438`) is never true.
   - LiveSplit game time stays paused for endings 2 and 3, and the on-screen timer is permanently stopped.

Ending splits still fire, but the game-time comparison for an All Endings run is wrong. If the game sends the player back to `Sewer_Start` after an ending, B-4 also resets the whole run.

**Fix:** Decide explicitly which categories are supported. If multi-ending runs should work, only stop timers on the *final* ending, which the category or a config option must define. Do not leave `isLoading` stuck: clear it in `HandleEnding`, or let `OnScreenTimer.Update` clear `isLoading` regardless of `IsRunActive`. See also Q-3, which proposes a single run state machine.

### B-4 — High — Loading `Sewer_Start` resets the LiveSplit run unconditionally *(Confirmed in code; reachability: Verify)*

`AutoSplitter.cs:90-93` and `OnScreenTimer.cs:47-50`:

```csharp
if (scene.name == "Sewer_Start" && mode == LoadSceneMode.Single) StartRun();
```

`StartRun()` sends `reset` and `starttimer` to LiveSplit and restarts the on-screen timer. It does this whether or not a run is already in progress. Before `f4fdeb5`, the start condition was `currentScene == "Sewer_Start" && !gameStarted`, which ignored repeat visits.

This kills an in-progress run whenever `Sewer_Start` is loaded in `Single` mode. That happens in these cases:
- **Returning to the hub mid-run.** The comment in `Patches/QuitToMenu.cs:18-19` ("When returning to sewer_start, destroy duplicate instances") suggests this is a real path in the game. **Verify** which doors or deaths lead back to `Sewer_Start`.
- **Room Lock while standing in `Sewer_Start`.** `SceneLock` forces every door to reload `Sewer_Start` (`Patches/SceneLock.cs:15-21`), so every door resets LiveSplit.
- **Trainer room picker or J/K scene stepping** when it passes through `Sewer_Start` (`GUI.cs:175-186`, `GUI.cs:444`).

**Fix:** Start a run only on the transition from the title screen. That means a flag set in the `TitleScreenControler.StartGame` prefix, or by `TriggerInstantRestart`, and consumed on the next `Sewer_Start` load. Also gate the fallback in `UpdateAutosplitter` (`AutoSplitter.cs:388-391`) the same way.

### B-5 — Medium-High — Connecting mid-run zeroes LiveSplit game time *(Confirmed)*

`AutoSplitter.cs:139-140` sends `getcurrenttimerphase` and then `setgametime 0` every time a connection succeeds. That includes manual "Connect to LiveSplit" clicks and the background auto-reconnect every 6 s (`AutoSplitter.cs:302-311`). If LiveSplit restarts or the socket drops mid-run, the reconnect overwrites the game time of the running attempt with 0.

The reply to `getcurrenttimerphase` is also discarded by `ReadLoopAsync` (`AutoSplitter.cs:157-172`), so that command has no effect.

**Fix:** Only send `setgametime 0` (or `initgametime`) as part of `StartRun`, right after `starttimer`. Better: read the reply to `getcurrenttimerphase` and resync. If LiveSplit says `Running` and `gameStarted` is true, send `setgametime <OnScreenTimer time>` instead.

> Related, **Verify:** LiveSplit's `starttimer` resets game-time initialisation. The current `StartRun` sends `unpausegametime`, `reset` and `starttimer`, with `setgametime 0` commented out (`AutoSplitter.cs:324`). Check in LiveSplit that game time is actually initialised for each attempt. If it is not, add `initgametime` after `starttimer`.

### B-6 — Medium — Splits that become due while disconnected fire together on reconnect *(Confirmed)*

`Update()` only calls `UpdateAutosplitter()` while connected (`AutoSplitter.cs:313-316`). The `got*` flags are set only when a split is sent. `AttemptSendCommand` drops commands while disconnected, but the flags are only evaluated while connected.

Suppose a player collects the key, two items and 20 fruit during a 20-second LiveSplit drop. When the connection returns, all four splits are sent in consecutive frames, each at the wrong time. Separately, splits are not gated on `gameStarted`, so they can fire during practice too.

**Fix:** Evaluate split conditions every frame, regardless of connection. Record *when* each condition became true. On reconnect, decide whether to send or to skip stale splits, or at least log it. Gate all splits on `gameStarted`.

### B-7 — Medium — `currentSceneName` is taken from additive loads *(Confirmed)*

`Autosplitter.OnSceneLoaded` sets `currentSceneName = scene.name` for **every** load, including the additive `Sewer_Start` sideload in `ReferenceManager.cs:56`. Three consequences:

- After a sideload, `currentSceneName` is `"Sewer_Start"` while the player is in a different room. The title-reset, start and ending fallbacks in `UpdateAutosplitter` all act on the wrong name.
- **Concrete path:** from the title screen (`gameStarted == false`), use the room picker to load any room. `ReferenceManager` sideloads `Sewer_Start`, `currentSceneName` becomes `"Sewer_Start"`, and the fallback at `AutoSplitter.cs:388-391` calls `StartRun()`. Opening a practice room from the title screen therefore resets and starts the LiveSplit timer.
- The additive load also reaches the final `else` branch and sets `justLoadedScene = true` for a scene the player is not in.

**Fix:** Ignore `LoadSceneMode.Additive` in `Autosplitter.OnSceneLoaded`, or always use `SceneManager.GetActiveScene().name`, as the pre-`f4fdeb5` code did.

### B-8 — Medium — The sideload path can recurse, skip cleanup and grab the wrong `Player` *(Likely / Verify)*

`ReferenceManager.OnSceneLoaded` (`ReferenceManager.cs:41-68`) has three problems:

1. **Early return skips cleanup.** When the sideloaded `Sewer_Start` itself fires `sceneLoaded`, the first `if` runs again. If `FoodControl` does not exist yet, which is plausible because the comment at `QuitToMenu.cs:18` says `PersistControl` creates it on `Start`, the code queues **another** additive `Sewer_Start` and `return`s **before** reaching `CleanUpSideloadedScene`. The result is several copies of `Sewer_Start` with live walls, cameras and audio listeners ("2 audio listeners" warnings, visual overlap). It can repeat until some `Start()` creates a `FoodControl`.
2. **Wrong player.** `RefreshReferences()` runs *before* the cleanup and uses `FindGameObjectWithTag("Player")`, which returns an arbitrary match. If `Sewer_Start` contains its own player rig, `ReferenceManager.Player` can end up pointing at the sideloaded player. Cleanup then deactivates that player, so Store/Restore Position stops working.
3. The sideloaded `FoodControl` lives in the additive scene. Unless `PersistControl` marks it `DontDestroyOnLoad`, it is unloaded with the next `Single` load, and the sideload repeats in every room.

**Fix:** Keep a `sideloadInProgress` flag. Skip the sideload logic for the sideloaded scene itself. Run cleanup first. When resolving `Player`, prefer objects in `SceneManager.GetActiveScene()`. Consider `DontDestroyOnLoad` on the sideloaded `FoodControl` and `PersistControl` roots.

### B-9 — Medium — The timer pauses on a trigger, so it stays paused if no load follows *(Verify)*

`DoorBehavior.OnTriggerEnter` and `EndingTeleporter.OnTriggerEnter` prefixes call `NotifyLoadingStarted()` for any collider tagged `Player` (`Patches/AutoSplitter.cs:27-47`). The `TrainMapScript` prefix pauses on a Fire1 press when a destination is highlighted (`:57-77`).

Pausing on the trigger rather than on the actual load is presumably intentional, so that the fade-out is not counted. But if the original method decides **not** to load the next scene, game time stays paused until the next completed load, and real gameplay time is dropped from the loadless timer. Examples: a locked door, a door that needs the key or a cost, a train selection cancelled the same frame, or the game's own `OnTriggerStay` missing a `GetButtonDown` that the mod saw (physics steps and frames do not line up one to one).

**Verify** in the decompiled game when each of these methods actually calls `LoadScene`. Prefer a postfix, or a patch on the coroutine or method that performs the load, so the pause matches what the game really does. As a safety net, add a timeout: if no `sceneLoaded` arrives within N seconds of a pause, resume and log a warning.

### B-10 — Medium — `WinRoom1` and `Credits` count as endings for one timer but not the other *(Confirmed in code; route: Verify)*

`OnScreenTimer.IsEndingScene` (`OnScreenTimer.cs:61-69`) returns true for `winroom1` and `credits`, plus anything containing `"ending"`. The explicit `plaguending`, `spaceending` and `truending` checks are redundant because all three contain `"ending"`.

So:
- `OnScreenTimer.OnSceneLoaded` stops the on-screen timer on `WinRoom1` and `Credits`.
- `Autosplitter.HandleEnding` only splits on the three ending scenes. For `WinRoom1` it does nothing. Because that branch was taken, the `else { justLoadedScene = true; }` at `AutoSplitter.cs:102-105` is also skipped.

If `WinRoom1` comes before a final ending scene in a route, the on-screen timer stops there while LiveSplit keeps running. LiveSplit game time is also still paused from the door into `WinRoom1`, for the reason given in B-3. The two timers report different final times.

**Fix:** Keep one authoritative list of ending scenes per category in one place. Make both timers stop on exactly the same event.

### B-11 — Medium — Culture-sensitive `ToLower()` breaks default binds on some locales *(Likely)*

`SafeGetKeyDown` (`GUI.cs:129-140`) calls `bind.Trim().ToLower()`. Under the Turkish culture (`tr-TR`, and `az` too), `"I".ToLower()` is `"ı"` (dotless i) and `"INSERT".ToLower()` is `"ınsert"`. Neither is a valid Unity key name, so `Input.GetKeyDown` throws, the exception is swallowed, and the binds silently never fire. On those systems the default **Open Trainer** (`INSERT`) and **Remove Cheese** (`I`) binds are dead. This assumes the Mono runtime honours the OS culture, which Unity's Mono typically does on Windows.

The same applies to the other `ToLower()` and `ToUpper()` calls on identifiers: `ReferenceManager.cs:45`, `AutoSplitter.cs:88`, `AutoSplitter.cs:394`, `OnScreenTimer.cs:45`, `InventoryOverlay.cs:163`, and the `.ToUpper()` label calls in `GUI.cs`.

**Fix:** Use `ToLowerInvariant()` and `ToUpperInvariant()`, or `string.Equals(a, b, StringComparison.OrdinalIgnoreCase)`. Better still, see P-2: parse binds to `KeyCode` or BepInEx `KeyboardShortcut` once.

### B-12 — Medium — Hotkeys still fire while typing in trainer text fields *(Confirmed)*

`GUIComponent.Update` polls `Input.GetKeyDown` for every bind regardless of IMGUI keyboard focus. `CursorLockFix` only blocks mouse-look (`Patches/CursorLockFix.cs:37-46`). While the user is typing in the seed box or any bind box:

- Typing a letter that is bound runs that action. With the defaults, `j` or `k` **loads another scene**, `u/i/o/p` change cheese and fruit, `z/x` teleport, and `l` toggles Room Lock.
- Typing a space (for example in a key name like `left shift`) triggers **QuickStart** on the title screen (`Patches/QuickStart.cs:18-24`) and jumps in-game. WASD still moves the player.
- Bind fields are written live, one keystroke at a time (`GUI.cs:364-390`). While the user is replacing `INSERT`, the open-trainer bind is briefly `I`, `IN` and so on. Intermediate values that happen to be valid keys become active binds for that moment.

**Fix:** Skip all hotkey processing, and patch out QuickStart and player input, while `GUIUtility.keyboardControl != 0` or while the trainer window is open. Edit binds in a temporary string and commit on Enter or an Apply button, with validation (see A-5). Ideally use a "press a key to bind" capture button instead of free text.

### B-13 — Medium — Trainer cheats are on by default and leave no trace *(Confirmed)*

`TrainerEnabled` defaults to `true` (`Plugin.cs:91`), and the trainer hotkeys are bare letter keys: U, I, O, P, L, Z, X, J, K. Commit `8b78eb5` gated the binds on `TrainerEnabled`, but the default is still on. A single accidental key press during a leaderboard run can add resources, teleport, lock a room or skip a room, and nothing on screen shows that it happened.

For a mod used in real runs this is a **run-integrity** issue. Moderators reviewing a video cannot tell whether trainer actions were used.

**Fix (any of these):**
- Default `TrainerEnabled` to `false`.
- Require a modifier such as Ctrl, or the trainer window to be open.
- Set a "practice" flag once any trainer action is used, and show a persistent on-screen marker (for example "PRACTICE" next to the timer) until the next restart from the title screen.

Also consider showing a small "SpeedRave 1.2.0 | Seed: N (set/random)" watermark during runs, which helps verification.

### B-14 — Medium — `Clear Save On Start` default contradicts the README *(Confirmed)*

- `README.md` says: "Clear Save on New Game (Disabled By Default)".
- The `f4fdeb5` commit message says "Created a dedicated ClearSaveOnStart config flag (defaulted to false)".
- The code (`Plugin.cs:85`) says `Config.Bind("Patches", "Clear Save On Start", true)`.

`true` keeps the behaviour from before `f4fdeb5`, when clearing was tied to Quit To Menu (default on). But users who rely on the README will lose their save on New Game, and with B-2, all their PlayerPrefs on F6.

**Fix:** Decide on the default and make the code, the README and the config description agree. Add a description to the `Config.Bind` call explaining exactly what is deleted.

### B-15 — Low-Medium — Disabling the Autosplitter does not stop it *(Confirmed)*

Unchecking "Enable Autosplitter" in the Config UI only stops reconnect attempts and the startup connect. `Update()` keeps calling `UpdateAutosplitter()` while connected (`AutoSplitter.cs:313`), so splits, resets and pauses keep being sent. Fix: when the setting turns off, call `Disconnect()` (subscribe to `SettingChanged`), and gate `UpdateAutosplitter` on the setting.

### B-16 — Low-Medium — `SetSeed` depth counter leaks if a patched `Start()` throws *(Confirmed)*

`StoreState` and `RestoreState` (`Patches/SetSeed.cs:24-71`) are a Harmony prefix and postfix. If a patched `Start()` throws (for example a game NRE in one room), the postfix does not run. `stateDepth` then stays above 0, Unity's global RNG stays swapped to the seeded stream for the rest of the session, and `messyState` is never restored. Later random calls in `Update()` then consume the seeded stream, so seeds stop reproducing.

**Fix:** Use a `[HarmonyFinalizer]` for the restore step, which always runs, or check `stateDepth` on each `sceneLoaded` and reset it there. Also note the general design risk: determinism depends on the hand-maintained list of ten patched `Start` methods (`SetSeed.cs:24-33`). Any room that uses `Random` in `Awake`, `OnEnable` or in an unlisted class is not seeded. Worth auditing against the decompiled game.

### B-17 — Low-Medium — Inventory overlay uses the texture as the key for an item *(Likely)*

`InventoryOverlay` stores `sprite.texture` per item (`InventoryOverlay.cs:222-229`) and later removes items with `displayList.IndexOf(item.texture)` (`:258-266`). If the item sprites are packed into one atlas, which is common in Unity, every item has the *same* texture. Losing one item then removes the first matching entry, and its UV rect, which may belong to another item, so the wrong icon disappears. The UV calculation also assumes a tightly packed, non-rotated sprite.

**Fix:** Keep a `List<ItemDef>` of collected items instead of parallel texture and UV lists. Read the public bools directly (`foodControl.hasDuck` and so on), as `Autosplitter` does, instead of using reflection (see P-4).

### B-18 — Low — Timer display can jump about 1 s ahead for a frame *(Confirmed)*

`OnScreenTimer.FormatTime` (`OnScreenTimer.cs:229-242`) combines `TimeSpan.FromSeconds(seconds)` with `hundredths = (int)((seconds % 1f) * 100f)`. On .NET Framework and Mono, `TimeSpan.FromSeconds` **rounds to the nearest millisecond**. For `seconds = 59.9996`, the `TimeSpan` becomes `00:01:00.000` while `hundredths = 99`, so the display reads `01:00.99`, about one second ahead, for that frame. This happens in a 0.5 ms window every second, so at 60 fps it shows as an occasional flicker.

The `float` round trip (`CurrentTime => (float)stopwatch.Elapsed.TotalSeconds`) also discards precision for no benefit.

**Fix:** Format directly from `stopwatch.Elapsed`: `ts.Minutes`, `ts.Seconds`, `ts.Milliseconds / 10`, and `(int)ts.TotalHours`.

### B-19 — Low — `FoodControl` duplicate handling *(Likely)*

`QuitToMenuPatch.FoodControlStartPatch` (`Patches/QuitToMenu.cs:12-28`) has three issues:

- `FindObjectsOfType` order is **not guaranteed**. `persistControls[Length - 1]` may be the original `PersistControl`, not the duplicate.
- The prefix returns `void`, so the original `FoodControl.Start` still runs on the instance being destroyed. That can load save data and run `RefreshValues`. The `SetSeed.addSeedText` postfix then creates `foodControlSeedText` under the doomed instance and **overwrites the static** that points at the survivor's text, so later `UpdateSeedText` calls stop working.
- `FoodControlUpdatePatch` (`:30-63`) has the same pattern: it destroys the object and loads the title screen, but the original `Update` still runs that frame.

**Fix:** Return `bool` from these prefixes and return `false` after destroying. Pick the duplicate deterministically, for example the one that is not in the `DontDestroyOnLoad` scene, or the one that is not `__instance`'s sibling.

### B-20 — Low — Smaller bugs *(Confirmed)*

- **FPS box:** `fpsInput` starts as `"-1"` (`GUI.cs:117`), not `Plugin.TargetFPS.Value`, so the Config UI misreports a configured cap.
- **Window dragging:** the scene and config windows have their `x/y` overwritten every frame (`GUI.cs:227-228`, `:234-235`), so their `GUI.DragWindow()` calls do nothing. See also A-2.
- **Negative resources:** `ModifyFruit` and `ModifyCheese` can push values below 0 (`GUI.cs:612-626`).
- **Labels can crash:** `Plugin.LockBind.Value.ToUpper()` and the similar label calls (`GUI.cs:560-583`) throw an NRE if a string config value is null, for example after a hand-edited config. The restart label handles this; the others do not.
- **LiveSplit disconnect not detected:** `ReadLoopAsync` exits on a 0-byte read but does not mark the connection as down. `IsConnectedToLivesplit` stays true until a later write fails, so the first commands after LiveSplit closes are silently lost. The auto-reconnect also does not start until then.
- **Background read loop:** `Task.Run(() => ReadLoopAsync(stream, netCts.Token))` (`AutoSplitter.cs:137`) reads the `stream` and `netCts` *fields* lazily on a thread-pool thread. If `Disconnect()` runs first, `netCts.Token` throws an NRE that goes unobserved, and after a fast reconnect it could capture the *new* token. Capture locals before `Task.Run`.
- **QuickStart double start:** QuickStart calls `StartGame()` on every Space press (`Patches/QuickStart.cs:20-23`). If `StartGame` starts a fade or coroutine, a second press during it may call it again. That regenerates the random seed, because `Init` runs again, and may double-load. **Verify.**
- **Remove Music:** it only mutes loops that are already playing at `Start` (`Patches/RemoveMusic.cs:15`). Music that starts later is not muted. Turning the option off does not restore volume until a reload. It also mutes looping ambience and sound effects, not just music.
- **Cursor lock:** `CursorLockFix` forces the cursor to lock when the trainer closes (`:26-32`), even if the game had it unlocked, for example with the inventory menu open.
- **Dead seed check:** `lastRandomSeed != 0` (`GUI.cs:490`) treats a random seed of 0 as "none". Cosmetic.

## 2. Security

The mod's attack surface is small. It talks only to `127.0.0.1:16834`, never parses data it receives (responses are discarded), loads two PNGs from a local folder and reads the local BepInEx config. No critical security issues were found. Notes:

- **S-1 (Low) — Data destruction:** `PlayerPrefs.DeleteAll()` on a global hotkey. See B-2. This is the most "security-relevant" issue, as an integrity and availability risk for user data.
- **S-2 (Low) — Main thread can block:** `NetworkStream.Write` and `Flush` are synchronous on Unity's main thread (`AutoSplitter.cs:226-229`, `:248-251`, `:278-284`), and `SendTimeout` is not set (the default is infinite). If the local peer stops reading, for example a hung LiveSplit or a different program listening on 16834, the game's main thread can freeze. Set `client.SendTimeout`, or move all writes to a dedicated writer task with a `BlockingCollection` or channel.
- **S-3 (Low) — Unauthenticated localhost peer:** any local process can listen on 16834 and receive the commands. The commands contain nothing sensitive, so this is acceptable. Mention the port in the README so users know what to allow in their firewall.
- **S-4 (Low) — Texture path:** `AppDomain.CurrentDomain.BaseDirectory` + `BepInEx/CustomTextures` (`InventoryOverlay.cs:64`) depends on how the process was launched. Use `BepInEx.Paths.BepInExRootPath`, or the plugin's own directory, for a deterministic path. Image decoding uses Unity's `LoadImage` on user-supplied local files, which is an acceptable trust boundary.
- **S-5 (Low) — Supply chain and distribution:**
  - Releases are built on a developer machine from DLLs at a hard-coded Steam path (Q-1). There is no CI, no reproducible build and no checksum next to `SpeedRave.zip`.
  - The README links to BepInEx releases without pinning a version.
  - Recommended: build in CI against BepInEx's NuGet feed (`BepInEx.Core`, `BepInEx.PluginInfoProps`, `UnityEngine.Modules`) plus a stripped or publicized game assembly; publish SHA-256 hashes; state the tested BepInEx version, for example 5.4.x x64.
- **S-6 (Info) — Exceptions swallowed:** `SafeGetKeyDown` and `Disconnect` use empty `catch` blocks, which hide failures, including legitimate bugs. Log at Debug level instead.

## 3. Performance

- **P-1 — Medium — The config file is rewritten while dragging sliders or typing.** BepInEx `ConfigFile.SaveOnConfigSet` defaults to `true`. Each Config UI control writes back to `Plugin.X.Value` on every `OnGUI` pass (`GUI.cs:292-390`). Assigning the same value is a no-op, but **while a slider is dragged the value changes every pass**, and each change triggers a full synchronous rewrite of `SpeedRave.cfg`. That is several disk writes per frame, which causes hitches. Typing in bind or text fields also saves on every keystroke, including invalid intermediate values.
  - This also makes the "SAVE TO CONFIG" button misleading, because changes are already persisted as they happen.
  - **Fix:** set `Config.SaveOnConfigSet = false` in `Awake` and keep the explicit Save button. Or edit local copies and apply on release or Enter.
- **P-2 — Medium — Invalid binds throw an exception every frame.** `Input.GetKeyDown(string)` parses the key name on every call. For an unknown name it **throws** `ArgumentException`, which `SafeGetKeyDown` catches. With one or more bad binds, the mod throws and catches 60 to 600+ exceptions per second, for up to 11 binds. Even valid names are string-parsed every frame.
  - **Fix:** use BepInEx `ConfigEntry<KeyboardShortcut>` (built-in, supports modifiers, validated), or parse to `KeyCode` once on `SettingChanged`.
- **P-3 — Low-Medium — Per-frame garbage in OnGUI.** `OnGUI` runs at least twice per frame (Layout and Repaint, plus input events). It allocates on each pass:
  - `OnScreenTimer`: `string.Format` and `SceneManager.GetActiveScene().name`.
  - `InventoryOverlay`: `int.ToString()` and string interpolation.
  - The trainer window: many interpolated labels with `ToUpper()`.
  - These are small, but GC spikes show up as stutter, which matters in a speedrun mod. Cache the formatted timer string and rebuild it only when the displayed hundredth changes. Cache labels and rebuild them on `SettingChanged`.
- **P-4 — Low — Reflection with boxing every frame.** `InventoryOverlay.CheckInventoryState` calls `FieldInfo.GetValue` for six fields every frame (`InventoryOverlay.cs:244`). Each call boxes a `bool`. These fields are public, and `Autosplitter` already reads them directly.
- **P-5 — Low — Global object scans.**
  - `Resources.FindObjectsOfTypeAll<Font>()` runs every 5 s forever if the game font is never found (`InventoryOverlay.cs:155-173`). Cap the retries.
  - `FindObjectsOfType` is called in `FoodControl.Start` and in `RemoveMusic` on every scene. That is acceptable per load, but worth noting.
- **P-6 — Low — LiveSplit command latency.** Each queued LiveSplit command waits one frame because of `await Task.Yield()` (`AutoSplitter.cs:286`). A burst such as `StartRun`'s three commands, or the reconnect burst in B-6, spreads over several frames and can reorder against the "immediate" pause and unpause writes. Write the whole queue in one go, or route everything through one ordered writer.

## 4. Accessibility and UX

- **A-1 — No UI scaling.** All IMGUI sizes are fixed pixels: the 275×600 main window, the 320×500 config window, the 1100×350 room selector, the 32 px seed flash, and the 20–80 px timer. At 4K the trainer is tiny; at 720p it is cramped. Add a "UI Scale" option and apply `GUI.matrix = Matrix4x4.Scale(...)`, or scale the default skin's font sizes.
- **A-2 — Windows can end up offscreen and cannot be dragged.** The room selector is forced to `y = winRect.y + 610`, which is about 630 px or more down. On 720p and many laptop screens it is mostly offscreen, and because its position is reset every frame (B-20), the user cannot drag it back. The main window has no scroll view, so its contents clip if they grow.
- **A-3 — Colour-only timer state.** The on-screen timer shows "loading" only by turning yellow and "finished" only by turning green (`OnScreenTimer.cs:170-181`). Yellow on white has low contrast. Add a non-colour cue, for example a small "⏸" or "✓" glyph or a "LOAD" label, and/or let users set the colours.
- **A-4 — Mouse-only trainer.** The trainer windows cannot be used from the keyboard or a controller. The open bind is keyboard-only, and controller players have no way in. Consider controller-friendly binds, or keyboard navigation of the main actions.
- **A-5 — Bind editing gives no feedback.** Binds are free text, and an invalid key name is silently ignored (P-2). Show a red "invalid key" hint next to the field, or use a capture button ("Press a key…"). List the valid names in the README.
- **A-6 — The seed flash is too short.** It lasts 1.0 s, including a 0.25 s fade (`GUI.cs:715`). That is short for reading or recording a 10-digit seed. Make the duration configurable, and consider keeping the seed visible in a corner during set-seed runs (see B-13).
- **A-7 — Decorative fonts and a fixed layout.** The timer and overlay use the game's decorative font ("autumn" or "larua") when it is found. Offer a plain-font option for readability. The fixed seed text offsets (`-760f` in `SetSeed.cs:181`, and positions based on `Screen.width/2` at `FoodControl.Start` in `SetSeed.cs:115-119`) move or clip at non-default resolutions, or after a resolution change.

## 5. Code quality and maintainability

- **Q-1 — The build depends on one developer's machine.** `SpeedRave.csproj` hard-codes `C:\Program Files (x86)\Steam\steamapps\common\Sewer Rave\...` for every reference. Introduce a `$(GameDir)` property set in an untracked `SpeedRave.csproj.user` or `Directory.Build.props.user`. Reference BepInEx, Harmony and Unity from the BepInEx NuGet feed, and use a publicized game assembly. Consider moving to an SDK-style csproj.
- **Q-2 — No CI and no tests.** There is no GitHub Actions workflow, so nothing compiles on push. The pure logic could be extracted and unit-tested without Unity: time formatting, seed LCG, ending detection, split conditions, and the run state machine (Q-3). B-1, B-3, B-4 and B-18 would all have been caught by such tests.
- **Q-3 — Run state is scattered across classes.** It lives in public mutable statics and instance fields in three classes:
  - `Autosplitter`: `isLoading`, `justLoadedScene` and the `*Ending` flags are static; `gameStarted`, `timerPaused` and the `got*` flags are instance fields.
  - `OnScreenTimer`: `IsRunActive`, `IsEnded`.
  - `GUIComponent`: `locked`, `showGUI`.
  - `OnScreenTimer.Update` mutates `Autosplitter.isLoading`. Two separate `sceneLoaded` handlers each decide independently when a run starts, stops or ends.
  - This is the root cause of B-3, B-4, B-7 and B-10. Recommend one `RunState` class with explicit states (`Idle → Running ⇄ Loading → Finished`) and events. LiveSplit and the on-screen timer should be two listeners on it.
- **Q-4 — Dead or unused code.**
  - `Autosplitter.debug` is never set.
  - `endingCount` is incremented but never read.
  - `Plugin.mls` is created but unused; the code calls `UnityEngine.Debug.Log` directly.
  - `GUIComponent.sceneIndex` as a field: it only needs to be a local.
  - `parsedSeed` as a field: it only needs to be a local.
  - The commented-out `setgametime` lines.
  - `SetSeedPatchs.lastRandomSeed` is public but only read from the GUI.
  - There are unused `using`s in `QuickStart.cs`, `SceneLock.cs` and others.
- **Q-5 — Logging is inconsistent.** Use the BepInEx `ManualLogSource` (`mls`) everywhere, so logs carry the plugin prefix and log levels apply. Some messages are gated on `Plugin.Debug`; others always print. `Init` logs every seed, and `QuitToMenu` logs "SaveGame method not found!" without a `[SpeedRave]` prefix.
- **Q-6 — Names.**
  - `AutoSplitterPatchs` and `SetSeedPatchs` are typos ("Patches").
  - Two files are named `AutoSplitter.cs` (root and `Patches/`).
  - `Plugin.Debug` shadows `UnityEngine.Debug` inside `Plugin`, which forces fully-qualified calls.
  - The class is `GUIComponent` but the file is `GUI.cs`.
  - The patch class is `SceneLock` while the GUI uses `locked`.
- **Q-7 — Versions are out of sync.** `modVersion = "1.2.0"` (`Plugin.cs:15`), but `AssemblyVersion` and `AssemblyFileVersion` are `1.0.0.0` and the copyright says 2024 (`Properties/AssemblyInfo.cs`). Generate them from one source.
- **Q-8 — The solution references a deleted file.** `SpeedRave.sln` lists `ClearInventory.cs` as a Solution Item, but that file was renamed to `InventoryOverlay.cs` in `bc0d105`. Visual Studio shows it as missing.
- **Q-9 — Config is not validated.** Most `Config.Bind` calls have no description. Numeric entries have no `AcceptableValueRange` (`IconSize`, `TextHeight`, `Padding`, `TimerFontSize`, `TargetFPS`), so a hand-edited config can set negative or huge values. The GUI sliders clamp, but the file does not.
- **Q-10 — Prefixes that never skip.** Several prefixes return `bool` that is always `true`, while others that *should* skip the original return `void` (B-19). Use `void` prefixes when not skipping, and `bool` with deliberate `false` returns when the original must not run.

## 6. What is in good shape

- The Harmony patches are small, targeted and use cached `FieldInfo`s with null-safe fallbacks.
- The on-screen timer uses `Stopwatch` (real time, unaffected by `Time.timeScale`), and its fixed-width character slots prevent jitter. The idea is good.
- The LiveSplit networking keeps a reader draining the socket, which avoids filling the receive buffer, and handles errors with disconnect and reconnect.
- The seeding approach (swapping `Random.state` around a fixed set of `Start` methods) is a sound, non-invasive way to get set seeds, with nesting handled through `stateDepth`.
- The title text "SEWER RAVE+" makes modded runs identifiable on video, which is good for verification.
